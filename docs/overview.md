# 총괄 지시서

탈탈(임시 이름)을 구현하는 기준을 정한다. 모든 개발 작업은 이 문서에서 시작한다.

> 이 재료들을 어떻게 다 먹지? 산 재료를 나눠 쓰는 요리 3~5가지를 알려 드려요.

## 제품

탈탈은 장을 보고 직접 요리하는 사람이 산 재료와 양을 넣으면, 그 재료를 여러 요리에 나눠 쓰는 3~5가지 요리 묶음을 추천하는 모바일 웹 서비스다.

사람들은 재료를 묶음으로 사지만 요리는 일주일에 한두 번 한다. 산 재료를 다 쓰려면 며칠에 걸쳐 여러 요리에 나눠 써야 하는데, 레시피 검색은 한 번에 한 요리만 보여 주므로 나눠 쓰는 계획은 사람이 머릿속으로 세워야 한다. 그 사이 빨리 상하는 채소가 먼저 버려진다.

설문에서 확인한 내용은 다음과 같다. 응답은 35건이고 그중 31명이 요리한다. 표본이 작고 치우쳤을 수 있어 전체 사용자를 대표하지는 않는다.

- 요리하는 31명 중 23명(74%)이 최근 한 달 안에 재료를 버렸다.
- 요리하는 31명 중 17명(55%)이 주 1~2회만 요리하고, 이 중 13명이 재료를 버렸다.
- 재료를 다 쓰려고 따로 하는 일이 없다고 답한 9명 중 8명이 재료를 버렸다.
- 이 문항에 답한 25명 중 24명은 냉장고 재료로 요리를 추천하는 앱을 써 본 적이 없다.

## 지켜야 할 제품 원칙

제품의 차별점은 세 가지다.

1. 레시피를 한 개씩 늘어놓지 않고, 재료를 나눠 쓰는 요리 묶음 하나를 추천한다.
2. 요리마다 쓴 양을 빼고, 묶음이 끝나면 무엇이 얼마나 남는지 보여 준다.
3. 빨리 상하는 재료를 쓰는 요리를 앞 순서에 둔다.

화면을 만들 때는 다음 원칙을 따른다. 원칙이 서로 부딪히면 임의로 고르지 않고 사용자에게 확인한다.

1. 남는 양을 먼저 보여 준다. 결과 화면에서 남는 재료는 요리 목록보다 위에 둔다.
2. 요리를 한 묶음으로 읽히게 한다. 요리 카드를 고를 수 있는 후보처럼 보이게 하지 않는다.
3. 사야 할 것과 모르는 것을 숨기지 않는다. 추가 재료는 요리 카드에 적고, 추정한 양은 추정이라고 적는다.
4. 매일 요리한다고 가정하지 않는다. 화면에 날짜와 요일을 쓰지 않고, 요리는 "N번째 요리"로 부른다. 이 순서는 추천이고 지켜야 하는 규칙이 아니다.

## 전체 흐름

```text
[소개] ──▶ [시작 홈] ──직접 고르기──▶ [재료 입력] ──요리 찾기──▶ (계산 중) ──▶ [추천 결과]
 첫 방문만                                 ▲  │                     │              │
                                           │  └▶ 재료 선택 시트      │              ├▶ 사용량 시트
                                           │                        ▼              └▶ 레시피 상세 시트
                                           └──────────────── 오류, 추천 없음, 재료 수정
```

화면은 다음 네 개다.

- 소개
- 시작 홈
- 재료 입력
- 추천 결과

재료 선택, 사용량, 레시피 상세는 모든 화면 너비에서 바텀시트로 연다.

모든 화면은 1단이고, 휴대폰 폭을 기준으로 만든다. 데스크톱에서는 가운데 448px 열로 보여 준다.

### 화면 사이의 상태

| 상태 | 저장 위치 | 유지 범위 |
| --- | --- | --- |
| 입력한 재료, 수량, 단위, 인분 | 브라우저 메모리 | 계산 중, 오류, 결과, 재료 수정을 오가는 동안 유지한다. 새로고침하면 초기화한다 |
| 방문 여부 | 쿠키 | 3일 동안 유지한다. 그 안에 다시 방문하면 소개를 건너뛴다. 서버가 화면을 보내기 전에 확인한다 |

재료는 저장하지 않는다. 사용자는 다시 방문하면 재료를 새로 입력한다.

### 브라우저 뒤로가기

소개를 뺀 화면과 바텀시트를 브라우저 기록에 넣는다. 휴대폰의 뒤로가기는 앱을 나가지 않고 열린 시트를 닫거나 이전 화면으로 돌아간다. 이때 입력한 재료는 유지한다.

## 범위

이번 범위에서 만드는 것은 다음과 같다.

- 첫 방문 소개와 시작 홈
- 재료 검색과 여러 개 선택, 수량 입력, 인분 선택
- 3·4·5가지 요리 묶음 추천과 비교
- 사지 않는 묶음과 조금 사는 묶음 전환
- 다 쓰는 재료와 남는 재료 요약, 재료별 사용량
- 요리 순서와 빨리 상하는 재료 이유
- 레시피 상세
- 오류와 추천 없음 복구
- 유저 테스트용 사용 기록 수집(Microsoft Clarity)

범위 밖의 기능은 만들지 않는다.

- 사진이나 영수증으로 재료 입력. 화면에는 "준비 중" 표시만 둔다.
- 입력 저장, 결과 저장, 로그인
- 요리 하나만 다른 레시피로 바꾸기
- 6가지 이상의 묶음, 가짓수 자동 결정
- 구매 단위 표시, 산 재료가 묶음 뒤에 남는 양 계산
- 요리 카드별 "여기까지 하면 남는 양"
- 양념 보유 확인 화면, 양념 분량의 인분별 환산

## 기술 구조

```text
[빌드 스크립트]  원본 데이터에서 앱용 JSON을 만들어 비공개 데이터 저장소에 둔다
[배포]           GitHub Actions가 비공개 저장소의 JSON을 data/app/으로 복사한다
[서버]           가진 재료에 맞는 후보 레시피와 레시피 상세를 응답한다
[브라우저]       후보 레시피로 요리 묶음을 탐색하고 결과를 보여 준다
```

서버는 레시피 전체를 브라우저로 보내지 않고, 탐색에 필요한 후보 레시피만 보낸다. 레시피 상세는 사용자가 연 요리 하나만 보낸다.

로컬에서는 `data/app/`의 실제 데이터를 쓴다. 이 폴더가 없으면 API가 오류를 돌려준다. 프로덕션은 배포할 때 비공개 저장소에서 받은 데이터를 쓴다. 그래서 실제 데이터는 이 저장소에 커밋하지 않는다.

## 문서 지도

| 알고 싶은 것 | 문서 |
| --- | --- |
| 제품, 범위, 전체 흐름 | `docs/overview.md` |
| 폴더 구조와 의존 규칙 | `docs/architecture.md` |
| 앱 데이터 형태, 추천 함수와 처리 규칙 | `docs/data-contract.md` |
| 색, 서체, 간격, 컴포넌트 상태, 일러스트 | `docs/design.md` |
| 말투 규칙과 화면 문구 | `docs/copy.md` |
| 기능과 화면별 요구사항 | `docs/requirements/` |
| 화면 배치 참고 자료와 파일별 설명 | `docs/wireframes/README.md` |
| 기능별 구현 스펙 | `docs/specs/` |

문서마다 맡은 범위의 유일한 기준이다. 와이어프레임은 화면 배치를 참고하는 자료이고, 그 안의 문구, 수치, 색은 기준이 아니다. 문서끼리 어긋나는 곳을 찾으면 임의로 고르지 않고 사용자에게 확인한다.

`docs/requirements/`는 무엇을 만들지 정하고, `docs/specs/`는 어떻게 만들지 정한다. 구현 스펙은 개발 작업을 시작할 때 요구사항 문서에서 만든다.

## 구현 순서

추천 로직은 `features/find-meals`에, 서버 API는 `_app/api-routes`에 있다. 코드 위치는 `docs/architecture.md`를 따른다. 화면 작업은 아래 순서로 한다. 앞 단계가 끝나야 다음 단계를 시작하고, 같은 단계의 작업은 나란히 진행할 수 있다.

| 단계 | 요구사항 | 내용 |
| --- | --- | --- |
| 1 | `foundation.md` | 토큰, 폰트, 앱 레이아웃, 공통 컴포넌트, 화면 전환과 상태 |
| 2 | `onboarding.md`, `ingredient-input.md` | 소개, 시작 홈, 재료 입력 |
| 3 | `results.md`, `recipe-detail.md` | 추천 결과, 사용량 시트, 레시피 상세 |
| 4 | 이 문서 | 전체 점검 |

각 작업은 자기 요구사항 문서의 확인 기준을 지킨 뒤 끝낸다. 결과 화면은 재료 입력이 넘겨주는 실제 입력으로 확인하기 위해 2단계 뒤에 만든다.

### 전체 점검

화면을 오가야 보이는 문제와 전체 일관성을 마지막에 확인한다.

- 소개부터 레시피 상세까지 한 번에 지나가며, 재료 수정과 뒤로가기를 섞어도 입력이 유지되는지 본다.
- 실제 휴대폰에서 가상 키보드, 시트 스크롤, 포커스 복귀를 확인한다.
- 화면마다 색, 서체, 간격, 버튼 상태가 `docs/design.md`와 같은지 본다.
- 화면 문구가 `docs/copy.md`의 말투 규칙을 지키는지 본다.
- 키보드만으로, 그리고 화면 읽기 프로그램으로 처음부터 끝까지 쓸 수 있는지 본다.
